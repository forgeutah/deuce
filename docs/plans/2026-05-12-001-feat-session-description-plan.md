# feat: Add session description

## Summary

Add an optional `description` field to sessions that captures a short "what is this session for?" note, persisted on the `sessions` table, set via the Create Session dialog, and rendered as subtle secondary text under the session name in the sidebar. Empty descriptions hide the secondary line so existing sessions look unchanged.

---

## Problem Frame

Sessions are the primary unit of work in Deuce, but the only label users see is a short kebab-case slug (e.g. `auth-module`, `checkout-fix`). Once a user has more than a handful of sessions, the slug alone is not enough to remember what each one is investigating. A short description under the name — Slack-channel-topic-style — gives a low-effort way to keep that context visible without opening the session.

---

## Requirements

- **R1.** Sessions can carry an optional free-text description, stored on the `sessions` row.
- **R2.** The Create Session dialog exposes a "what's this for?" input. Leaving it blank is valid and stores an empty string.
- **R3.** The session sidebar renders the description on its own line directly beneath the session name, styled as subtle/secondary text and visually subordinate to the name. When the description is empty, no extra line is rendered and the card height matches today's layout.
- **R4.** The existing `PATCH /api/sessions/:id` endpoint accepts a `description` field so the value can be edited later by any future UI without backend changes.
- **R5.** WebSocket `session_update` events carry the description so other connected clients see edits without a refresh (this already happens implicitly — the field rides along inside the `sessionResponse` payload).

---

## Key Technical Decisions

- **Storage shape: new `description TEXT NOT NULL DEFAULT ''` column.** Mirrors the `repo_url` precedent in `server/internal/db/migrations/003_add_session_repo_url.sql` and the `plan_content` shape already on the table. NOT NULL with empty-string default keeps Go zero-values clean and lets the frontend treat empty as "no description" without a null check.
- **Edit path reuses the existing PATCH handler.** `UpdateSession` already accepts a struct of optional `*string` fields and broadcasts a `session_update` event. Threading description through that handler avoids inventing a new endpoint and gives a future "edit description" UI a turn-key API.
- **Display surface is sidebar only for this cut.** The user explicitly described "under the session name" — the sidebar is the surface where that layout exists. The CenterPanel header (`# {name}`) is a single inline title and is deliberately left untouched here.
- **Search continues to match name only.** Extending the existing `searchQuery` filter to also match description is a reasonable follow-up but is not part of this scope (see Deferred to Follow-Up Work).

## Implementation Units

### U1. Migration and SQL queries

**Goal:** Add the `description` column to the `sessions` table and update sqlc queries so the field flows through generated Go code.

**Requirements:** R1

**Dependencies:** none

**Files:**
- `server/internal/db/migrations/005_session_description.sql` (new)
- `server/internal/db/queries/sessions.sql` (modify `CreateSession`; the existing `SELECT *` queries pick the column up automatically)
- `server/internal/db/*.sql.go` (regenerated by `make generate`)

**Approach:**
- Add `description TEXT NOT NULL DEFAULT ''` in the `-- +goose Up` block; drop it in `-- +goose Down`.
- Extend the `CreateSession` query's column list and `VALUES` to include `description` as a new parameter. The existing `SELECT *` patterns in `GetSession` and `ListSessionsForUser` pick the new field up without edits.
- Run `make generate` so the regenerated `db.Session` struct and `CreateSessionParams` expose `Description`.

**Patterns to follow:** `server/internal/db/migrations/003_add_session_repo_url.sql` for the migration shape; the existing `CreateSession` query for parameter ordering.

**Test scenarios:**
- Test expectation: none — pure schema + generated-code change; behavior is exercised by U2 and U4 tests.

**Verification:** `make migrate` succeeds; `make generate` produces a clean diff with `Description` on `db.Session` and `db.CreateSessionParams`; `go build ./...` passes.

### U2. Backend: thread description through handlers and response

**Goal:** Accept `description` on create, accept it on PATCH, and include it in every `sessionResponse`.

**Requirements:** R2, R4, R5

**Dependencies:** U1

**Files:**
- `server/internal/handler/sessions.go`
- `server/internal/handler/sessions_test.go` (new or extend if present)

**Approach:**
- Add `Description string \`json:"description"\`` to `sessionResponse` and populate it from `db.Session.Description` in `buildSessionResponse`.
- Add `Description string \`json:"description"\`` to `createSessionRequest` and pass it through `db.CreateSessionParams` in `CreateSession`.
- Add `Description *string \`json:"description"\`` to `updateSessionRequest`. When non-nil, call a new `UpdateSessionDescription` query that mirrors `UpdateSessionStatus` / `UpdateSessionPlan` (one-line `UPDATE ... RETURNING *`). Reuse the same broadcast path so connected clients receive the updated payload.

**Patterns to follow:** The existing `UpdateSessionStatus` / `UpdateSessionPlan` query + handler branch in `server/internal/handler/sessions.go` is the template for both the new sqlc query and the new handler branch.

**Test scenarios:**
- `POST /api/sessions` with a non-empty `description` returns 201 and the response body's `description` field matches the input.
- `POST /api/sessions` omitting `description` returns 201 and the response's `description` is `""`.
- `PATCH /api/sessions/:id` with `{"description": "new text"}` returns 200, the response body reflects the new value, and `GetSession` afterward returns the same value.
- `PATCH /api/sessions/:id` with `{"description": ""}` clears a previously-set description (no special "null" semantics needed since the column is NOT NULL).
- `PATCH /api/sessions/:id` with only other fields (e.g. `status`) leaves description unchanged.

**Verification:** Unit/integration tests above pass; `make build` passes; manual `curl` against `make dev` matches the test scenarios.

### U3. Frontend types, API wrapper, and Create Session input

**Goal:** Surface the description on the `Session` type, accept it in the `createSession` API wrapper, and add an optional input to the Create Session dialog.

**Requirements:** R1, R2

**Dependencies:** U2

**Files:**
- `src/types/index.ts`
- `src/lib/api.ts`
- `src/components/session/CreateSessionDialog.tsx`
- `src/mocks/data/seed.ts` (add `description` to mock session objects to keep the type consistent)

**Approach:**
- Add `description: string;` to the `Session` interface alongside `name`.
- Add `description?: string` to the `createSession` body type in `src/lib/api.ts`. No new endpoint — `updateSession` already takes a free-form body object, but for clarity also add `description?: string` to its typed body.
- Add a short single-line input directly below the Session Name input in `CreateSessionDialog`. Label it "Description" with a placeholder like "What's this session for?". Pass it to `api.createSession({ ..., description })`. Empty string is fine.
- Reset the description value in `resetForm()`.
- Update mock seed objects so TypeScript stays happy (set `description: ""` or short example strings).

**Patterns to follow:** Existing Session Name input markup at the top of `CreateSessionDialog.tsx`; matching label classes (`text-xs font-medium text-foreground-muted`) and input classes (`bg-background-input border-border-muted text-foreground`).

**Test scenarios:**
- `npx tsc --noEmit` passes after the type addition (compile-time proof the field flows everywhere it needs to).
- Manual: open Create Session with a description filled in → session appears in the sidebar with the description rendered (covered by U4 test scenarios too).
- Manual: open Create Session with description blank → session is created and the sidebar card looks identical to today's layout.

**Verification:** Type check is clean; the dialog renders the new field; a created session round-trips description through the backend (verified together with U2).

### U4. Sidebar: render description under session name

**Goal:** Render the session description as subtle secondary text beneath the session name in the sidebar's `SessionCard`.

**Requirements:** R3

**Dependencies:** U3

**Files:**
- `src/components/layout/SessionSidebar.tsx`

**Approach:**
- Restructure the `SessionCard` button so the name+description occupy a two-line vertical stack on the left, with the status dot and unread badge remaining on the right.
- The current single-row layout uses `flex items-center` with `# icon`, name, status dot, unread badge. Split the middle column into a `flex flex-col` containing the name (current styling, `truncate font-medium`) and, when `session.description` is non-empty, a second line styled with `text-xs text-foreground-subtle truncate` (or `line-clamp-1`) so it renders subdued and never wraps.
- When `session.description` is empty, omit the second line entirely so the card height is identical to today's layout — existing sessions must look unchanged.
- Keep the hash icon and the right-side cluster vertically centered relative to the whole card.

**Patterns to follow:** The existing `SessionCard` markup and the GitHub Primer color tokens already used (`text-foreground-subtle` for muted secondary text, per `src/styles/globals.css` and the Project Group "uppercase tracking-wider text-foreground-subtle" usage).

**Test scenarios:**
- A session with a non-empty description renders two lines: name in current styling, description below it in subtle/muted styling, both truncated.
- A session with an empty description renders a single-line card visually identical to today's layout (no extra padding, no empty second line collapsing weirdly).
- Long descriptions truncate with ellipsis on a single line and do not wrap or push the status dot / unread badge out of position.
- Active-session styling (`bg-background-emphasis border-l-2 border-accent`) still applies cleanly to the whole two-line card.
- Status dot and unread badge remain right-aligned and vertically centered for both single- and two-line cards.

**Verification:** `npm run dev`, open the sidebar with at least one session that has a description and one that doesn't, eyeball both states match the scenarios above; `npm run lint` and `npx tsc --noEmit` pass.

## Scope Boundaries

**In scope**
- Schema column, generated sqlc code, handler create + PATCH support, response payload, type, API wrapper, Create Session dialog input, sidebar rendering.

### Deferred to Follow-Up Work
- Inline rename / "edit description" UI in the sidebar (the PATCH endpoint is ready; no UI in this cut).
- Extending the sidebar search filter to match description text in addition to name.
- Description rendered in the CenterPanel header, breadcrumbs, or any other surface besides the sidebar.
- A dedicated "session settings" panel.

### Outside this product's identity
- Markdown / rich-text formatting inside the description — sessions are workspace channels, not documents. Plain text only.

---

## System-Wide Impact

- **WebSocket payload** — `session_update` events now include `description`. Clients that already trust `sessionResponse` will pick this up for free; clients that explicitly destructure fields would not, but `src/stores/session-store.ts` replaces sessions wholesale so this is safe.
- **Mock seed** — `src/mocks/data/seed.ts` must include `description` on every seeded session to keep the `Session` type satisfied.
- **No auth changes, no migrations of existing rows** — the default empty string handles existing sessions without backfill.

---

## Risks

- **None material.** The change is additive at every layer with an empty-string default. The largest risk is the sidebar layout change in U4 inadvertently shifting vertical alignment for descriptionless sessions — mitigated by an explicit "no second line when empty" test scenario.
